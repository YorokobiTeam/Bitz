# Game data contract v1

This contract defines the JSON objects shared by the Unity game and a future game server. The machine-readable source of truth is [game-data-v1.schema.json](game-data-v1.schema.json), using JSON Schema draft 2020-12. Select the relevant object with `#/$defs/Map`, `#/$defs/PlayerInfo`, `#/$defs/PlayerSetting`, or `#/$defs/MapScore`. Validate complete objects with a JSON Schema validator configured to assert the `uuid` format. A list response is an array of the corresponding objects; a missing object should be represented by the endpoint's status, not an invented empty DTO.

The game currently accesses Supabase directly. These shapes are based on its PostgREST column mappings; no separate game server or HTTP API is implemented in this repository. The schema specifies data only, not routes, authentication, authorization, transport, partial-update payloads, or database defaults. Those require agreement when the server is implemented.

All listed properties are required on complete objects, including nullable properties. UUIDs are JSON strings in standard UUID format. Scores and experience are signed 32-bit integers. Nullable strings reflect what the current C# models can represent; they do not establish database constraints. Unknown properties are allowed so consumers can ignore additive fields. Producers must not change a field's name, type, or meaning in v1; introduce a new contract version for breaking changes. Validate on both sides and pin the same contract revision in each build.

`Map` corresponds to the `map` table. `is_offline` is client-local and is excluded from the server DTO. `PlayerInfo` corresponds to `player_info`, `PlayerSetting` to `player_setting`, and `MapScore` to `player_map_score`. The existing score model uses strings for its IDs, so this version does not claim they are UUIDs. The game also has an older `BitzPlayerInfo` model for login, whose IDs are strings; the server must send UUID strings for `player_info` so both representations can read them. Storage metadata, beatmap chart files, account sessions and telemetry are outside this contract until their server behavior is agreed.

## Keeping implementations aligned

Run `node Contracts/check-game-data.js` from the repository root in the game CI. It compares the schema's field names and types with the game's PostgREST models, and checks explicit JSON names where present. It does not validate serialization libraries, actual payloads, or the server. The server repository must consume this same versioned schema, validate representative serialized responses against each definition in its own CI, and run compatibility tests against the game before release. A schema change must update the models and both sides' tests together. This repository cannot enforce checks in a server repository that has not yet adopted the contract.
